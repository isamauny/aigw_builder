# aigw-builder

A CLI that builds WSO2 API Platform (AI) Gateway images with policies selected from the [WSO2 Policy Hub](https://wso2.com/api-platform/policy-hub), driven by a single YAML file. It resolves each policy to an exact release, generates the `build.yaml` used by the official gateway build tool, and runs [`ap gateway image build`](https://wso2.com/api-platform/docs/api-gateway/1.1.0/policies/custom-policies/building-gateway-with-custom-policies/).

## Requirements

- Python 3.11+
- Docker (running)
- The `ap` CLI on your `PATH` ([releases](https://github.com/wso2/api-platform/releases))
- `git` (used to look up policy release tags)
- For supported images: an existing `docker login` to the supported registry (e.g. `docker login registry.wso2.com`). The tool never handles registry credentials.

## Install

Dependencies are pinned, with hashes, in `requirements.lock` (runtime) and `requirements-dev.lock` (runtime + tests). Install from the lock file so you get exactly the audited versions:

```bash
uv venv --python 3.11
uv pip sync --require-hashes requirements-dev.lock     # or requirements.lock for runtime only
uv pip install --no-deps -e .
source .venv/bin/activate
aigw-builder --help
```

Without uv: `python3.11 -m venv .venv && .venv/bin/pip install --require-hashes -r requirements-dev.lock && .venv/bin/pip install --no-deps -e .`

### Updating dependencies

Regenerate the lock files, then audit them before committing:

```bash
uv pip compile pyproject.toml --universal --python-version 3.11 --generate-hashes -o requirements.lock
uv pip compile pyproject.toml --extra dev --universal --python-version 3.11 --generate-hashes -o requirements-dev.lock
uvx pip-audit -r requirements-dev.lock --require-hashes --disable-pip
```

Add `--upgrade` to the compile commands to move to the newest allowed versions. If an audit finding is fixed in a newer release, raise the minimum version in `pyproject.toml` too.

The [Dependency audit](.github/workflows/dependency-audit.yml) GitHub Actions workflow runs this audit every Monday at 07:00 UTC, on pushes and pull requests that change `pyproject.toml` or the lock files, and on demand from the Actions tab. It fails when a pinned version has a known vulnerability or when a lock file no longer matches `pyproject.toml`. Findings are listed in the run summary.

## Browsing the Policy Hub

```bash
aigw-builder categories                     # all categories with policy counts
aigw-builder policies -c Guardrails         # policies in one category
aigw-builder policies -c AI -c MCP          # several categories (OR)
aigw-builder policies -s routing            # free-text search
aigw-builder show semantic-cache            # versions + parameters of one policy
```

Every listing command accepts `--json`. Set `--hub-url` or `WSO2AP_POLICYHUB_BASE_URL` to point at a different Policy Hub.

## Seeing which policies an image already has

```bash
aigw-builder inspect ghcr.io/wso2/api-platform/gateway-controller:1.1.0
aigw-builder inspect -f aigw.yaml           # base image of the config, diffed against the config
```

Policies are read from the **controller** image: from `/app/build-manifest.yaml` when present, otherwise from the policy definitions in `/app/policies` or `/app/default-policies`. The runtime image compiles its policies into a binary and cannot be listed.

## Building an image

```bash
aigw-builder init                           # writes ./aigw.yaml with every option documented
aigw-builder init --template team.yaml      # or start from your own template
aigw-builder validate -f aigw.yaml          # resolve every policy, show the plan
aigw-builder build -f aigw.yaml --dry-run   # write + print build.yaml and the ap command, no build
aigw-builder build -f aigw.yaml             # build
```

The resulting images are `<output.repository>/<gateway.name>-gateway-controller:<output.tag>` and `<output.repository>/<gateway.name>-gateway-runtime:<output.tag>`; `output.tag` defaults to `gateway.version`. By default `output.repository` is `localhost`, so the images stay in your local image store and nothing is pushed. `local` (which Docker expands to `docker.io/local`) is treated the same way. To publish, set `output.repository` to a registry and run `build --push` (or set `push: true`).

### Build files for review

Every build keeps two files in `aigw-build/<gateway.name>/` next to the config (or in `output.build_files_dir`):

- `build.yaml`: generated by aigw-builder. It lists the base images and every policy pinned to an exact release, and is what `ap` builds from.
- `build-manifest.yaml`: written by `ap` after a successful build. It records the exact policies baked into the image; the same file is in the controller image at `/app/build-manifest.yaml`.

Both are overwritten by the next build. `build --dry-run` writes `build.yaml` only, so you can review it before building. Commit the folder alongside your config if you want changes reviewed in pull requests.

### Building on top of a base image

The gateway build **replaces** the policy set of the base image; it does not add to it. With `base_policies: keep` (the default), aigw-builder reads the policies already in the base controller image and carries them over, then applies your `policies` on top:

- a policy in your list that is also in the base image overrides its version (shown as upgraded, downgraded or unchanged)
- policies in `exclude_base_policies` are dropped
- everything else is kept at its exact current version

Use `base_policies: none` to build an image with only the policies you list.

## Checking for and applying policy updates

Like `brew outdated` / `brew upgrade`:

```bash
aigw-builder outdated ghcr.io/wso2/api-platform/gateway-controller:1.1.0   # policies in an image
aigw-builder outdated -f aigw.yaml          # policies the config would build (base image + your list)
aigw-builder outdated -f aigw.yaml --all    # include up-to-date policies

aigw-builder upgrade -f aigw.yaml --dry-run # rebuild with base policies moved to newer releases
aigw-builder upgrade -f aigw.yaml --to patch

# Start from a previous build instead of the stock base image
aigw-builder outdated -f aigw.yaml --from last
aigw-builder upgrade -f aigw.yaml --from last --to minor
aigw-builder upgrade -f aigw.yaml --from docker.io/local/demo-ai-gateway-gateway-controller:1.2.0.12

# Upgrade an earlier build as is, without a config: same policies and base images, new tag
aigw-builder upgrade --from localhost/my-ai-gateway-gateway-controller:1.2.1 --to patch --tag 1.2.1-p1
```

For each policy, `outdated` shows the newest release at three levels:

- **patch**: newest `vX.Y.*`
- **minor**: newest release published on the Policy Hub within the same major version
- **latest**: the Policy Hub's latest release, which can be a new major version

`upgrade --to patch|minor|latest` (default `minor`) builds with the carried-over base policies moved to that level.

By default the carried-over policies are read from the configured base controller image. `--from` (on `outdated -f`, `upgrade` and `build`) reads them from another controller image instead, typically one you built earlier, so you upgrade what you actually run. `--from last` means the previous build of this config on this machine (`<output.repository>/<gateway.name>-gateway-controller:<output.tag>`). It must exist locally and is never pulled; any other image is used locally if present, otherwise pulled. The new build still uses the configured base images; only the policy set comes from the `--from` image, with your `policies` and `exclude_base_policies` applied on top. Policies you pin under `policies` are never changed. To make this permanent, set `upgrade_base_policies` in the config (default `none`, which keeps builds reproducible).

Without `--file`, `upgrade --from <image> --tag <new tag>` (and `build`, which then rebuilds without upgrading) needs no config at all. The image must be a controller image built by `ap` (`<repository>/<name>-gateway-controller:<tag>`). The name and repository come from the image reference, and the base images from the `build.base-image` and `build.builder-version` labels that `ap` puts on the controller and runtime images. Every policy in the image is carried over and moved to the `--to` level. `--tag` is required and must differ from the image's own tag, so the earlier build is never overwritten. `build.yaml` is written to `aigw-build/<name>/` under the current directory. Policies that were built from a local path cannot be rebuilt this way; use a config with a `path:` for them.

## Configuration reference

[config/aigw.reference.yaml](config/aigw.reference.yaml) documents every option with its default value and the allowed values, ready to copy. `aigw-builder init` writes the same file as `./aigw.yaml`. Only `gateway.version` is required.

### Starting from an example

The two commented examples are complete, working configs. Use either one as a template for your own:

- [examples/aigw.public.yaml](examples/aigw.public.yaml): public images (`ghcr.io`, no login needed), base policies kept with one excluded, AI policies added or upgraded, local output.
- [examples/aigw.supported.yaml](examples/aigw.supported.yaml): supported (WSO2 subscription) images with per-component base image tags, base policies patch-upgraded at build time, TypeSafe Jev policies added, local output.

```bash
aigw-builder init --template examples/aigw.public.yaml -o aigw.yaml      # public images
aigw-builder init --template examples/aigw.supported.yaml -o aigw.yaml   # supported images
```

Then edit `aigw.yaml` before building:

1. Set `gateway.name`, which names the output images.
2. Set `gateway.version` and, for supported images, the per-component tags under `images` to the release you want.
3. Change `policies` (browse with `aigw-builder policies -c <category>`) and `exclude_base_policies`.
4. Set `output.repository` (and `output.tag` if needed) for where the images should go.
5. Run `aigw-builder validate -f aigw.yaml`, then `aigw-builder build -f aigw.yaml`. For supported images, run `docker login registry.wso2.com` first.

The examples are in the aigw-builder repository, not in the installed package. If you installed from a wheel, download the example file first, or use the team template approach below.

### Team templates

The reference documents the built-in defaults, so leave it as it is (a test checks that it matches them). To give a team its own starting point, such as your registry, image source, output repository and standard policies, keep a template file anywhere (for example, a copy of one of the examples, adjusted) and point `init` at it:

```bash
aigw-builder init --template ~/acme/aigw-template.yaml -o aigw.yaml
export AIGW_BUILDER_TEMPLATE=~/acme/aigw-template.yaml   # or set it once; --template wins if both are set
aigw-builder init
```

`init` checks that the template is a valid config before writing it, resolving relative paths from the output location. Use `--no-validate` to write it anyway, for example when it references local policy directories that only exist in your team's repository.

### All options

| Option | Default | Values |
|---|---|---|
| `gateway.version` | required | gateway release, e.g. `"1.1.0"`; default tag of base and built images |
| `gateway.name` | config directory name | output image name prefix |
| `image_source` | `public` | `public`, `supported` |
| `registries.public.prefix` | `ghcr.io/wso2/api-platform` | registry/namespace (only to override) |
| `registries.supported.prefix` | `registry.wso2.com/wso2-api-platform` | registry/namespace (only to override) |
| `images.builder` / `.controller` / `.runtime` | `<prefix>/gateway-<component>:<gateway.version>` | a tag (keeps the prefix) or a full image reference |
| `base_policies` | `keep` | `keep`, `none` |
| `exclude_base_policies` | `[]` | policy names |
| `upgrade_base_policies` | `none` | `none`, `patch`, `minor`, `latest` |
| `output.repository` | `localhost` (local only) | registry/namespace; `localhost` and `local` are local only, never pushed |
| `output.tag` | `gateway.version` | tag of the built images |
| `output.push` | `false` | `true` needs a registry repository (or pass `--push`) |
| `output.platform` | Docker host platform | host platform only, with push (see Troubleshooting) |
| `output.no_cache` | `false` | `true`, `false` |
| `output.output_dir` | none | directory |
| `output.build_files_dir` | `aigw-build/<gateway.name>/` | directory for `build.yaml` and `build-manifest.yaml` |
| `output.buildx_builder` | `auto` | `auto` or a buildx builder name |
| `policies[].name` | required | Policy Hub name |
| `policies[].version` | Policy Hub latest | `"1.2"`, `v1.3.1`, `v1` |
| `policies[].path` | none | local policy directory |
| `policies[].kind` | auto-detected | `go`, `python` |

Base images are `<registries[image_source].prefix>/gateway-{builder,controller,runtime}:<gateway.version>`. Under `images` you can give one component its own tag (for example `runtime: "1.1.0-3"`, keeping the prefix) or a full image reference. Relative paths are resolved against the config file's directory.

### How versions are resolved

The Policy Hub publishes `major.minor` versions (e.g. `1.2`). Policy releases are tagged in [wso2/gateway-controllers](https://github.com/wso2/gateway-controllers) as `policies/<name>/vX.Y.Z`. aigw-builder picks the newest tag that matches the requested version and writes an exact reference: a `gomodule` reference for Go policies, or a `pipPackage` reference for Python policies (detected by whether the release has a `go.mod`).

## Troubleshooting

**The build succeeds but the images are not in `docker images`.** `ap` builds with `docker buildx` and does not pass `--load`. With a `docker-container` buildx builder (the only kind available on Podman), the results then stay in the build cache. With `output.buildx_builder: auto` (the default), aigw-builder detects this and runs `ap` with `BUILDX_BUILDER=aigw-builder`, a builder it creates once with `--driver-opt default-load=true`. Your selected builder is not changed. To use your own builder instead, set `output.buildx_builder: <name>`.

**"Image not found ... project X not found" on the supported registry.** The registry answers like this when the image path is wrong, even if you are logged in. The default is `registry.wso2.com/wso2-api-platform`; if you set `registries.supported.prefix`, check it.

**A base image policy shows "not tagged upstream; using nearest release".** Stock images record the version that a floating `@vN` reference resolved to when the image was built. Some of those releases were later removed from wso2/gateway-controllers, so aigw-builder uses the nearest release in the same major.minor and shows it in the plan. To choose a different version, pin the policy under `policies`.

**`output.platform` is rejected.** `ap gateway image build --platform` always pushes (`buildx --push`), and its gateway-builder step compiles the policy-engine binary for the Docker host's CPU only. A cross-platform target (for example `linux/amd64` on an Apple Silicon Mac), or several platforms at once, would produce runtime images with a binary for the wrong CPU. aigw-builder therefore only accepts the host's own platform, together with `push`.
